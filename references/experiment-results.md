# Experiment results

## Extract and reuse

1. Read the experiment records accompanying or cited by the brief. ChatGPT's taskbook plugin publishes these as `tests/<test-name>.md` at the same Gitea commit as `taskbook.md`. Follow any cited headings. Treat commands, examples, and attachments as supporting material for the reported observations. A proposed check without an observed result remains open.
2. Before running an experiment, look for its result in the current taskbook and relevant `.audit/taskbook/` records in the implementation worktree. Check the behavior, entry point, code or artifact, inputs, configuration, and environment that matter to the conclusion. A different commit or machine can still satisfy those conditions. If they hold, record which conclusion you are relying on and use it for the matching decision or acceptance criterion. Skip that experiment. A historical failure only covers the baseline. Verify new behavior and changed conditions where a new check is needed, and run required repository checks without also running the same experiment separately. If applicability is uncertain before use, mark that coverage open and report the missing condition.
3. Keep a Markdown record under `.audit/taskbook/<owner>/<repo>/<taskbook-commit>.md` for results extracted from a Gitea taskbook. For a local source, use `.audit/taskbook/local/<intake-commit>.md`. For each result record the original path and heading, who ran it if known, the tested version and relevant conditions, the entry point or steps, the expectation and actual observation, and the conclusion with its coverage and limits. For a Gitea source include the source branch when known and a permanent link to the original file at the pinned commit. Keep failed and inconclusive observations as recorded. Preserve any existing record and add only missing information on resume. For an already archived result, cite its existing audit path in place of another copy.

Check the audit destination for collisions and symlinked parents. Keep the audit records in the implementation branch so later rounds can find them after the intake attachments are removed. When a later decision relies on a result, keep its audit path and original source at hand for reporting.

## Stop and report

Stop implementation and normal PR delivery as soon as an operation that relied on an experiment fails in a way that calls its conclusion into question. Use the observations already available to identify the conflict and the affected experiment file. A failure explained by an unrelated cause or an expected change in the experiment's conditions is handled by regular verification. When the evidence calls the conclusion into question, stop even if only part of the task is affected. Leave the original experiment intact and do not rerun it, retry the failing operation to reproduce it, or try a substitute experiment to validate the same claim.

1. Tell the user which experiment is suspect, what failed, and which work is blocked. Save a pending report in the task worktree under `.audit/taskbook/reports/`. Include the original path and heading, audit path, pinned Gitea source link or local source revision, original conclusion and conditions, the dependent operation and implementation revision, observed failure, why it raises doubt, and the affected work or acceptance. State what remains uncertain. Keep this report out of the implementation commits.
2. Use the local Magpie Gitea MCP for the entire report PR. Use the Gitea taskbook repository and branch that supplied the experiment. For an experiment with only a local source, use the project's Gitea taskbook branch if it can be verified from the current task. A SHA or tag alone does not name a PR base. Resolve the corresponding taskbook branch from the task context and Gitea before writing.
3. Record the chosen report branch and PR base in the saved report before writing to Gitea. Create the report branch from that taskbook branch. Commit only the report Markdown under `.audit/taskbook/reports/` with `create_or_update_file`. Open a PR from the report branch back to the taskbook branch with `pull_request_write` (`method: create`). Name the suspect source file in the PR and summarize the failure and its impact in the body. Keep the taskbook branch, experiment file, and implementation PR untouched. If the source branch advanced, cite the pinned revision in the report and note any relevant change already visible on the branch.
4. On retry or uncertain write, read back the report branch and look up the PR by head and base with `pull_request_read` (`method: get_by_branches`) before creating anything again. Reuse the report and PR for the same observation. In T3, link the PR immediately after creation with `link_pull_request`. Confirm the PR targets the taskbook branch and contains the report, then give the user the link and end the round.

If the taskbook branch or a required local MCP capability is unavailable, report the exact blocker and the saved report path, then end the round. On resume, use the saved report to recover or finish publication. Record the published PR link in the local report. A result with an unresolved report stays out of reuse, and the affected round stays stopped until the user or taskbook author supplies a resolution.
