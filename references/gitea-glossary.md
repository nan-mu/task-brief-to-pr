# Project glossary in Gitea

1. Through the local Magpie Gitea MCP, find the repository with the same name as the implementation project, using the repository lookup in [Gitea intake](gitea-intake.md). Use `ref: glossary` for glossary reads. Read the root `GLOSSARY-MAP.md` and follow it to the glossaries for the affected contexts. When there is no map, read the root `GLOSSARY.md`.
2. If `list_branches` confirms that `glossary` does not exist, use `create_branch` to create it from the Gitea default branch. This carries forward any glossary already stored there. If another session creates the branch first, reuse it. Read the glossary files on `glossary` before deciding what needs to be created or updated.
3. If the applicable glossary is missing, start Matt Pocock's `mattpocock-skills:domain-modeling` before implementing. Use the brief, project docs and code, and any existing project glossary to establish the first project-specific terms. When the first term is resolved, create the glossary in Matt's format at its mapped path, or at `GLOSSARY.md` in the root for a single context. Follow the same skill when defining, changing, or reconciling terms in an existing glossary. Give Matt's skills the glossary text or readable temporary copies with the same relative paths when they need local files.
4. Publish resolved terms with `create_or_update_file` and explicit `branch_name: glossary`. Include the existing file SHA for updates. If a concurrent edit changes the file, reread it and preserve both sets of terms. Read back the result on `glossary`. Keep taskbook branches read-only during glossary maintenance, including when a taskbook branch is the default branch.
5. If Gitea is unavailable or a glossary write is denied, use the available project terminology and resolved terms for implementation. Save any unpublished glossary draft outside the tracked files and report the blocker and draft path at handoff.
